# P0–P2：理论、实现与声明边界

本页以《TPAA说明书》的 G1–G4、D1–D6 和《智能体身份构建new.pptx》的目标为基准；
`tpaa_v1` 的公式修订见 [勘误](../protocol-errata/tpaa_v1.md)。此处的 P0–P2 是本轮
理论到实现的完善工作包，不是旧 README 里的历史阶段编号。

| 理论要求 | 代码落点 | 当前可声明的事实 | 仍缺什么 |
| --- | --- | --- | --- |
| 用户自主构造 AF、签署 CR | `crypto/tpaa_v1/proto_user.py`、`user_credential_handler/handler.py` | 协议算法和签名验证已实现；本地测试执行器持有 USER 种子 | 用户独立控制的密钥设备及每次操作的人在场确认 |
| TP 对现实身份进行核验 | `crypto/tpaa_v1/identity_evidence.py`、`identity_service` | 正式受理模式验证可信核验方签名的证据，并绑定 H(ID)、用户公钥、TP 槽位和 requestId；演练模式显式放行无证据的合成身份 | 实际证件/生物特征核验提供方、法律与运营流程 |

## 正式身份核验证据合同

核验方在用户获得 TP 槽位、确定 CR 的 `requestId` 后，独立核验自然人身份并签署
`IdentityEvidence`。签名体含 `issuer`、`result=verified`、`subjectHid`、`userSignPk`、
`tpNonce`、`requestId`、`method`、`assuranceLevel`、`evidenceRef`、`issuedAt`、`expiresAt`。
证据放在给 TP 的加密 CR 内，用户签名覆盖整份 CR。它不包含 PII 或 BI 明文。

TP 的可信核验方名录通过部署文件 `TPAA_IDENTITY_VERIFIER_TRUST` 注入，不能从 CR 接受
公钥。示例形状（公钥仅为占位符，不能直接用于启动）：

```json
{
  "minAssurance": "substantial",
  "issuers": {"approved-idv": "<Schnorr 验签公钥 hex>"}
}
```

`identity-service` 在 G2 受理和 G3 取件签发时均核验签名、信任名录、保证级别、
有效期及与本次 CR 的绑定。证据只是核验结果的可验证声明：**代码不自行识别人脸、
查验证件或证明核验方真正执行了其声称的步骤**。这些能力必须由正式核验服务提供。

## Portal 与钱包边界

本地 `test-adapter` 保留原有 PII/BI 表单及执行器流程，明确标记
`userControlledExecution=false`。`user-controlled` 模式只接受钱包预构造的 `cr`、
`walletLabel` 和 `requestId`，Portal 核对钱包保留的待处理密文摘要后转交 TP；
Portal 不接收明文 PII/BI。现有 `UserCredentialHandler` 始终报告服务端持钥，不能被
配置成 `user-controlled`。真正的钱包实现须独立持钥，并在 G1、D3、D5、D6、发布时
对申请与内容摘要要求用户确认；仓库当前没有这样的设备适配器。

## 验收与限制

- 单元测试：`tests/unit/test_identity_evidence.py` 检查签名篡改、未知签发方、
  错误身份/槽位/请求号、过期和保证级别不足；原有 v1 加密 CR 往返测试保持通过。
- 服务测试应覆盖：未配置可信核验方时正式模式拒绝启动；无证据或过期证据不能
  受理/签发；本地 test-adapter 仍能用合成身份跑通。
- P1 尚未达到“用户自主主权”验收门槛。当前完成的是安全边界和将来钱包接入的
  密文入口；在没有用户侧控钥设备与人确认接口前，系统只能声明为本地仿真。
