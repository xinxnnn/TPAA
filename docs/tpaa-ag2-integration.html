02 · 三层承诺与能力的真实含义

PHC / DID“是谁”。G3 先得初始 PHC，D4 把选配模块的 CMI 写进 APM，D6 后取得最终 PHC'' 与 did:wba；PHC.TPM 里存的是加密的 CDID，不是可直接展示的明文 DID。
CMI / build“由什么构成”。模块仓库的真实版本与内容摘要按确定顺序进入 HCGen；交付时核对安装字节、模块摘要、PHC.APM.CMI 与确定性 buildDigest。
Policy / tools“此刻允许做什么”。Manifest 里的工具、操作、连接器和权限必须是 AP 批准模块的允许子集；运行期开关只能在已签策略的边界内缩小权限，不能点击页面就凭空增添新的 PHC 能力。

一项可选能力至少包含：moduleId@version、仓库字节摘要、AG2 工具导出清单、真实执行器与就绪检查、权限/风险/审批策略、数据范围、连接器 secretRef。CMI 承诺模块构成，不自动承诺后来随意修改的工具策略。必须由 AP 对选定策略和 Manifest 另行核准并签署运行证明。

依据：errata E9/E10/N2；crypto/tpaa_v1/engine.py:194-201；crypto/tpaa_v1/schema.py:32-58,79-96；packages/tpaa_runtime/manifest.py:1-5,34-70,73-147；V6 §18.1–18.3。

03 · 用户申领主链：严格按 v1 顺序

G1 → G4用户钱包签加密 CR；TP 验证并经审核证据闸门发初始 PHC/TPAC；用户在 G4 校验签名、AF、归属与槽位并保存钱包凭证。此时尚未承诺所选 AG2 技能，也尚无最终 DID。
D1 → D3用户持钱包凭证签 AR 给 AP；AP 认证持有人并回密文 CMM（真实、未下架模块目录）；用户在 UI 选模块与版本，先展示风险、执行器状态、授权范围，再对选项和 CMM 版本签 PACI。AP 只从受信仓库取摘要，拒绝篡改/下架版本和重复“同身份 + 同选择”。
D4AP 按选择的有序模块计算 CMI = HCGen(CMC,H(ID))；算法 1 更新 PHC.APM（CMI、AFRef）并做 AF 重绑，AP 保留本地记录与开口；密文 PAR 回钱包。此处只承诺选到的模块，不把未连接的工具标成已就绪。
D5钱包验 PHC'、逐模块重算 CMI 与 AF/AFRef；确认通过才签并加密 DIDGR 给 TP。失败则停止签发，不把“不一致”自动修复成另一份。
D6TP 验 DIDGR，创建 CSCID / did:wba、把 DID 加密成 CDID、重封 ECID 并执行算法 2；用户钱包验最终 PHC''、解 CDID，得到 DID。只有钱包接受的最终凭证才可进入交付发布。
交付AP 以最终 DID 关联经认证的 D4 构建记录，确定性打包 agent.yaml、模块与摘要/版本。发布 最终 PHC 摘要、CMI、AFRef、有序模块摘要、实际 buildDigest、被批准的工具策略；一份制品可复验，但不包含用户明文身份、TP/AP 私钥或 Provider API Key。
模块目录不能把“可支持”当“可申领”现有工作台列出 22 项设计能力；只有与 CMM 仓库实际模块和可用 Connector 对应、且 AP 授权的选项才能提交 PACI。web.search 等待配置、desktop.control 非 AG2 原生的条目只能作为目录说明，不能进入已签发 CMI 或工具表。

依据：docs/protocol-map/tpaa_v1.md:12-30；crypto/tpaa_v1/proto_user.py:53-105,113-134,152-214；crypto/tpaa_v1/proto_ap.py:45-125；crypto/tpaa_v1/proto_tp.py:135-208；services/ap_side/agent_service/v1_app.py:60-141；errata E14/E15/E17。

04 · 用户拿到智能体后的运行装配

钱包已接受的 PHC'' + DID
  → 用户签挑战登录，运行服务核对会话 owner
  → AP 读取最终签发台账 / 只读已发布 build
  → 验 PHC 公开证明、DID↔PHC 的 TP 绑定、状态与父体状态
  → 重算安装模块摘要 → HCGen 与 PHC.APM.CMI 对齐
  → 重算 buildDigest → 核对发布记录；装配受批准的 Manifest
  → AP 核准 Manifest digest + 允许工具/策略，绑定临时会话公钥
  → AG2 Agent(tools=仅允许的已就绪工具) + Guard + Gateway
  → 运行；每次调用实时复核状态、scope、策略与确认

V6 §18.5 明确“读取 agent.yaml → CMI 三处对比 → 装配工具 → 注入运行服务 → 实例化 AG2 → 可运行”；现有 trust.py 已有同进程 DidBinding/运行证明演示，但生产服务不能把 TP/AP HSM 对象直接传给运行进程。应增加经鉴权的 TP 绑定声明 API 与 AP 证明 API，运行服务只使用公开验证材料和短期会话密钥。

启动失败处理

PHC 未完成 D6、owner 不符、模块字节变化、CMI/buildDigest 不符、证书过期或状态不新鲜，全部 fail closed。冻结并告警，不启动 Agent、不回退到静态 Demo DID。

升级和运行中开关

关闭已授权工具仅为运行时策略收紧；新版本/新模块/超原范围的工具需重新选配、再算 CMI、更新凭证与已发布制品。旧会话按版本钉住，不能借新开关获得越权能力。

依据：V6 §18.1–18.5；services/ap_side/agent_service/domain/services/build.py:27-84,96-135；packages/tpaa_runtime/trust.py:185-254；packages/tpaa_runtime/runtime.py:43-115；errata E8/E9。

06 · 可信协同与人工确认

发送主智能体发起协同前核本人状态、出站 scope、对端目录；签署含 from/to、nonce、期限、任务和运行证明引用的信封。AG2 可用 Hub/Channel/TransitionGraph 管编排，但网络可信判断由 TPAA 证明验证和专用 Arbiter/入口共同实施。
接收对端验 PHC、TP/AP 证明、Manifest digest、状态新鲜度、会话签名、有效期、重放与入站允许范围；回信绑定原请求 nonce。子体持独立 PHC/DID/CMI，父体吊销需级联停用；子体之间默认不得直连。
确认工具调用提交确认请求，不直接执行。票据绑定 owner、session、DID、Manifest digest、工具与准确参数摘要、Connector、到期时间、一次性 nonce。批准后原子核销，复查当前策略和状态，再经同一 Gateway 执行；拒绝/超时也审计。

不同的人类确认不能混用：G1 的审查批准（E17）、子体派生的显式人工知情确认（V6 §4/§9.3）、运行时高风险工具确认（V6 §18.3）分别绑定不同动作和证据；不能用“记住 7 天”代替逐次审批。

依据：V6 §4.1–4.5,§9.3,§18.3–18.4；errata E17/E18；packages/tpaa_runtime/trust.py:269-313；packages/tpaa_runtime/sandbox.py:56-84。

07 · 现有实现的断点，不能跳过

断点当前事实实施要求
权威申领链旧 proto0 申领链与 v1 G1–D6 同名不同义；README 还记载旧版 K5。选定 v1 为唯一发布路径；旧 API 标记为演示/迁移，不能把 proto0 产物直接当 v1 运行。
签发到交付AP v1 服务记录 D4 的 ApRecord，但未有“已接受 DID → 最终 PHC → build/策略”的发布台账。补完成/发布事务与跨 TP/AP/钱包的可重试、幂等、对账状态；关联原申请及 D5/D6 接受。
CMI 算法AG2 Manifest 的演示默认用 sha256(DID) 代替 H(ID)；旧 proto0 又有另一套 hash_chain。正式链路禁止该默认；只接受钱包/AP 验证过的 v1 CMI，并校验有序模块字节。
构建证明当前 Manifest.build_digest 摘要的是尚未写入 buildDigest 的草稿，而非可执行制品字节。以确定性 BuildPlan 的实际文件字节摘要为唯一 buildDigest；AP 验安装字节与其授权的工具策略。
Web 工作台run_ag2_workspace.py 无真实 PHC/owner 会话；API Key、草稿、确认在进程全局，确认请求不能安全对应当前用户。按 authenticated owner+DID+session 隔离；本地演示服务不得公网暴露；接入密钥引用和持久化审批。
动态状态StatusRegistry、信封 nonce 与待回复集在内存；IdentityGuard 只做局部状态/过期检查。新鲜状态证明或 fail-closed 查询，持久 nonce/会话/审计；启动和每次高风险调用验完整信任链与策略版本。

依据：issue_agent.py:75-188；services/ap_side/agent_service/v1_app.py:90-141；packages/tpaa_runtime/manifest.py:155-180；packages/tpaa_runtime/trust.py:163-182,238-254；packages/tpaa_runtime/runtime.py:43-65；demos/personal_agent/run_ag2_workspace.py:72-75,229-325。

08 · 分阶段实现与可验收证据

  1. P0 · 锁定协议与数据契约。核对说明书原件；将 v1 与 proto0 API/制品分开；冻结“模块→工具→执行器”规范、CMI 顺序、buildDigest 口径及用户/TP/AP 各自拥有的数据。验收：一个选择向量在钱包/AP/打包侧得到相同 CMI，顺序/字节篡改被拒。
  2. P1 · 完成 G1–D6 到发布。保持现有 v1 服务端签名/加密入口；补钱包接受后 DID→构建发布映射、幂等关联与认证。验收：完整 HTTP 申领后重启服务仍能以 owner+DID 取回最终 PHC、模块清单和 build；跨用户请求、重放、错误顺序均拒绝。
  3. P2 · 构建受信运行实例。已发布模块和工具策略核对 → TP DID 绑定 → AP 运行证明 → AG2 装配。验收：更换任意文件字节、偷加工具、过期/吊销或换 PHC，均在 Agent 启动前拒绝。
  4. P3 · 统一工作台和 Gateway。将现有 22 项目录改为 CMM/Connector 的实时投影；只让已签发且 ready 的能力进入 Agent；任务/确认/审计按 owner/session 绑定。验收：新会话工具清单与授权一致；未配置 Web 服务不显示“已执行”；跨会话确认和重复确认失败。
  5. P4 · 协同与生命周期。先做本地两 Agent 完整验签回路，再接 Hub/Channel 和跨服务路由；再做父子体级联/TTL/持久重放缓存。验收：合法 scope 成功、越权/篡改/重放/吊销均失败，重启后仍保留必要的状态与审计。
演示终点在浏览器里由用户完成 G4 → 选择真实可用能力 → D5 接受 → D6 获最终 DID → 一键启动 → 查看 AG2 实际工具轨迹 → 自己批准一次文件写入 → 两 Agent 验证协同 → 吊销后调用被拒。每一步都展示实际请求/状态/证据摘要，不展示私钥、H(ID) 或身份明文。

明确不在首轮宣称：Windows 桌面自动化、邮箱/日历/地图/图像服务、真实外网搜索已接通；这些必须由各自 Connector 与权限测试单独验收。
