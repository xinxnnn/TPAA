# 什么时候能在页面上把整套流程点一遍

## 先说结论

**按 A 轮那 7 步走，走完也到不了。** 不是因为步骤写得不对，是因为那 7 步的目标是"让链路可信"，不是"让链路能点"。它没有一步是前端接线或启动编排。

但好消息是：**你要的可视化，比 A 轮剩下的部分更接近完成。** 用户侧的主流程页面已经写完了，接的是真接口。卡住的地方只有一个，而且不在它的计划里。

## 一、四端前端体检（实测）

| 端 | 页面代码量 | 占位页 | 状态 |
|---|---|---|---|
| user-web（用户区） | 265 行 | 3 个（lifecycle / subagent / subagent.confirm） | **主流程已完整**，接真接口 |
| tp-web（TP 区） | 206 行 | 0 个 | 页面齐全，但**审核台是写死的数组** |
| ap-web（AP 区） | 60 行 | **4 个全占位** | 空壳 |
| ops-web（运营区） | 60 行 | **4 个全占位** | 空壳 |

`apps/ap-web/src/pages/*/index.tsx` 每个 15 行，内容是：

```
// subagent 页面占位（user-web / user 区）
// 说明：派生子智能体：选择能力、设定有效期

```

这是 `scripts/gen_frontend_skeleton.py` 生成的骨架，不是失败品，是还没填。

### user-web 已经做到什么程度

`apps/user-web/src/App.tsx` 是一个完整的流程机：左侧一条 11 格的进度轨（INIT / G1 / REVIEW / G3 / G4 / D1 / D2 / D3 / D4 / D5 / D6 / PUB），右侧按 `nextAction` 冒出下一步的按钮。

它调的 8 个动作，背后是真后端（`services/user_side/portal_api/app.py:364-371`）：

```
issue → accept-g4 → begin-agent → build-agent → accept-d5 → confirm-d5 → finalize-d6 → publish
```

而且页面上明写着 "REAL STATE / NO DEMO CREDENTIAL"，浏览器只调 user-zone，密码学材料不进页面。**这一页做完了。**

### 卡在哪

`portal_api/app.py:144` 每次刷新时间线都会去 TP 拉一次审核状态：

```python
review = self.ctx.tp.get(f"/v1/applications/{app_id}/timeline")
```

`_next_action`（`:168-186`）的第一条判断是：

```python
if states.get("REVIEW") == "approved" and "G3" not in states:
    return "issue"
```

**REVIEW 不变成 approved，后面 8 个动作全部不可达。**

而 tp-web 的审核台（`apps/tp-web/src/pages/review/index.tsx:17-21`）是这样开头的：

```typescript
const initial: DemoApplication[] = [
  { id: 'APP-7F2A91', alias: 'User · 83A1', ... },
```

界面上挂着「演示数据 · 未连接服务」的标签。它点"通过"只是改本地 state，不发请求。

**后端其实有接口**：`services/tp_side/review_service/app.py:54` 的 `POST /v1/reviews/{app_id}`。做完了，界面没接。

这就是全部断点。**一格，而且是闸门。**

## 二、后端缺的三块

### 1. HSM 种子文件 —— 一个都没有

`hsm_from_seed()`（`v1_http.py:186`）从 JSON 文件里按域取种子：

```python
data = json.loads(Path(env_required(env_var)).read_text())
return crypto.sdk.v1.hsm_from_seed(domain=domain, seed=data.get(domain.lower()) or {})
```

我全仓搜了 `schnorr_sk`，`--include=*.json` 零命中。`scripts/` 下也没有生成脚本。

**没有种子，七个服务一个都起不来**（缺项会直接 `raise RuntimeError`，代码里刻意不随机生成，因为重启后既有凭证全废）。

### 2. 启动编排 —— RUNNING.md 只讲前端

`scripts/run_demo.ps1` 只起 5173 / 5174 两个 Vite，一行业务后端都不起。

而 `production.py:build_context` 要这些环境变量才能装配：

```
TPAA_EXECUTOR_URL / TPAA_EXECUTOR_TOKEN / TPAA_EXECUTOR_OWNER
TPAA_TP_URL / TPAA_TP_AUTH_URL
TPAA_AP_URL / TPAA_AP_AUTH_URL
TPAA_PHC_URL / TPAA_PHC_AUTH_URL
TPAA_USER_STATE_ROOT / TPAA_USER_WORKFLOW_DB
TPAA_USER_AUTH_HSM_SEED
```

好消息：**每个服务都有模块级 `app` 对象**，uvicorn 直接指模块就能起，不需要 `if __name__`。

```
services/user_side/executor_service/app.py      → executor
services/tp_side/identity_service/app.py        → TP 提交与时间线（兼 TP 区 auth 入口）
services/tp_side/review_service/app.py          → 审核
services/tp_side/phc_service/app.py             → G3 签发
services/ap_side/agent_service/app.py           → D2/D4/发布（兼 AP 区 auth 入口）
services/user_side/portal_api/app.py            → 用户区编排（前端连这个）
```

六个进程，六个端口。全是 `LazyApp`，第一次请求才装配 —— 所以起进程本身很轻，装配失败会推迟到第一次访问才暴露。这一点在冒烟时要盯。

### 3. 种子文件生成脚本

四份种子（tp / ap / auth / user），每份含 `schnorr_sk`、`chameleon_sk`、`root`。可以放在一个 JSON 里，各域取自己那段。

## 三、三个里程碑，各自能验收什么

### M1 「能点完一次」

补齐上面三块，用脚本代替审核台：先 `curl` 打一次 `POST /v1/reviews/{app_id}`，再回浏览器点"刷新状态"，后面 8 步就都亮了。

**验收标准**：浏览器里从填表提交，一路点到"请求 AP 发布制品"，左侧进度轨 11 格全打勾，每格下面有 `phcVersion` / `did` / `cmi` 这些物证。

**这一档你就能录屏、能答辩。** 代价是审核那一下在命令行里敲，不在页面上。

### M2 「TP 侧也是真的」

审核台接 `/v1/reviews/{app_id}`：队列改从 `GET /v1/applications/{app_id}/review` 读，批准按钮调 POST。删除本地 `initial` 数组和「演示数据」标签。

**验收标准**：开两个浏览器窗口，左边 user-web 提交，右边 tp-web 队列里出现这条申请，点批准，左边刷新后能继续往下走。**全程不碰命令行。**

这一档才叫「整个流程可视化操作」。

### M3 「AP 与运营端」

ap-web / ops-web 的 8 个占位页填实：模块仓库、主智能体、子智能体、生命周期 / 模块审核、权限、统计。

再加上 user-web 的 `subagent`（派生）、`lifecycle`（吊销）、tp-web 的 `supervision`（追溯）。

**验收标准**：子智能体派生走完整申领流程、每次需要用户确认；吊销能让 DID 失效；追溯能按 DID 拉出协查流程。

这一档覆盖你课题里全部六类攻击场景的演示。

## 四、A 轮／B 轮 与这三档的关系

它们不是同一条线，但也不冲突。

| | 解决什么 | 对可视化的影响 |
|---|---|---|
| A 轮剩余（步骤 4–7） | 幂等、字段契约、Portal 对账、smoke | **步骤 4 的幂等直接决定演示时能不能乱点** |
| B 轮 | Portal 持久化与对账、executor contract | 演示稳定性 |
| M1 | 能让页面跑起来 | 从 0 到 1 |
| M2 | 审核台接真 | 从 1 到"完整" |

有一件事值得单独说：**步骤 4 的「requestId 持久幂等」不是安全洁癖，它对演示有直接价值。**

现在 `accept-rr` / `accept-final` 重放会二次执行。演示的时候人会手抖、会刷新、会连点两次 —— 一旦二次执行，时间线就乱了，而你要在答辩现场解释一个乱掉的时间线。**先做幂等，再开始演示。**

这也解释了另一件事：A 轮的 `assert_single_worker` 不会妨碍演示。它拦的是"同一个服务开多个 worker"，而我们要起的是六个不同的服务各一个进程。合法。

## 五、我的建议顺序

它现在要接着做步骤 4 剩余部分。这个安排不算错，但如果目标是"尽快看到整套流程"，我建议插一刀：

1. **先做种子生成 + 启动脚本**（M1 的地基）
   两个脚本，`gen_seeds.py` 约 50 行、`run_stack.ps1` 约 80 行。做完之后第一次能在浏览器里看到真的 PHC 和 DID —— 这个反馈对后面所有的调试都值钱。
2. **然后回到步骤 4 的幂等**
   有了可点的页面，幂等的重要性立刻变得具体：你会自己撞上重复点击。
3. **再补审核台接线**（M2）
   到这一步，"整个流程可视化"成立。
4. **之后才是 A 轮剩下的字段表、限长、对账，和 B 轮**

理由很简单：**现在的顺序是先修房子的防火，但房子还没有门。** 防火该修，只是先装个门，你才能进去看防火修得对不对。

## 六、直接回答"什么时候"

- 想在浏览器里**看到一次完整的 PHC 签发到 DID 生成** → 补两个脚本（M1），当前就能做。
- 想**不碰命令行、两个窗口把流程点完** → 再加审核台接线（M2）。
- 想**把所有页面都点满**（子智能体、吊销、追溯、AP 侧、运营侧）→ M3，这是最大的一块，8 个占位页加上 3 个 user-web 占位页。

它那份 A 轮计划里，最接近"可视化"的是步骤 7 的「executor 独立进程 socket smoke + RUNNING.md」。那也只是冒烟，不是界面。**别把它当成可视化交付。**
