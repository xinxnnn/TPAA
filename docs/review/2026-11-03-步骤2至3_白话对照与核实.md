## 一、这一步在协议里的位置

你的全流程是：

```
G1 → G2 → G3 → G4 → D1 → D2 → D3 → D4 → D5 → D6 → FINAL → AP 发布 → runtime
```

它改的是 **D4 / D5 / D6 这三格之间的一个字段**，没加新阶段，没改流程顺序。

D4 是 AP 干活的阶段：AP 解开 AR、验 TPAC、验用户签名、算 CMI（式 8）、把 AF 重绑到 CMI 上（算法 1）、算 RF（式 9）、组装 PAR 加密回给用户。

它在这个阶段**多做了一件事**：AP 额外签一张声明，写明"这次我给她分配的域名是 X、模块清单摘要是 Y、她这份 PHC' 的摘要是 Z"，签名后放进 PAR 一起给用户。

这张声明就是 `D4Statement`。名字起得不算好，叫"AP 的分配回执"更好懂。

## 二、它补的那个洞，具体怎么打

假设你（用户）走一遍流程。`domain2` 是 AP 的域名，D6 会把它拼进 DID：

```python
# proto_tp.py:227
did = f"did:wba:{b64u(cscid)}:{domain1}:{domain2}"
```

也就是说：**DID 里写着"归哪个 AP 管"，而这一段字符串是从 `domain2` 抄来的。**

改动之前的链路（`proto_tp.py` 旧写法）：

1. AP 在 D4 阶段把 `domain2` 塞进 PAR 给你；
2. 你在 D5 拿到它，写进 DIDGR，签个名（`json_digest` 覆盖整个 body，所以这个字段确实在你的签名保护下）；
3. TP 在 D6 解 DIDGR，验你的签名，通过；
4. TP 取出 `domain2`，拼进 DID，签 DID。

第 3 步"验你的签名通过"是真的。问题是：**你的签名只能证明"这话是你说的"，不能证明"AP 真给过你这个域名"。**

于是攻击很朴素：你（或者一个被控的门户，它本来就在替你和 AP 之间传话）把 `domain2` 改成 `evil.example.com`，重新签一份 DIDGR。TP 验签名 —— 通过。TP 签 DID —— 你的 DID 挂在了自己的域名下。

后果不是"数据泄露"这么轻。DID 里的域名是这个身份的服务端点，D6 之后所有对它的解析都会打到那个域名上。它等于让"服务方是谁"变成用户自选。

这个洞在你的论文里没有明说，因为论文默认 AP 是半可信的。但你的威胁模型里 AP 并非全信 —— 协查必须 AP 配合才能交出 `s_ap`，这个设计本身就承认了 AP 会不配合。**一个可能不配合的 AP，它的分配结果就不能由用户代述。**

所以这不是工程洁癖，是威胁模型推导出来的缺口。

## 三、修好之后的链路

三段，各归一个责任方：

**AP（D4 末尾）**
签一张声明，字段是这些（`proto_ap.py:103`）：

```
version, applicationId, recordId, owner, userSignPk,
afRef, cmi, domain2, modulesDigest, phcDigest, issuedAt
```

签完连同 PAR 一起加密给你（`proto_ap.py:176-183`）。注意 `recordId` 是 AP 自己先定号再签 —— 这样这份声明是"认号不认人"的一次性凭证，换不到别的申请上去。

**用户（D5）**
你拿到 PAR，先做原来的事（验 PHC'、用 PA 里的模块重算 CMI、验 AF 开口），然后多做一步：验 AP 的签名，再把声明里每一项跟 PAR 里解出来的事实**逐项比对**（`proto_user.py:187-202`）：

```
owner / userSignPk / afRef / cmi / domain2 / modulesDigest / phcDigest
```

任何一项对不上就拒绝。这一步的意义是：**AP 不能当面一套背后一套**——给 TP 的声明和给你的 PAR 必须一致，否则你在 D5 就把它拦下来了。

然后你构造 DIDGR，把整份声明（含 AP 的签名）放进 body，自己再签一次（`proto_user.py:209-215`）。于是 TP 手里有两把签名，覆盖的是同一份内容。

**TP（D6）**
验 AP 签名 → 逐项跟自己 G3 的记录对齐（`proto_tp.py:210-223`）：

```python
if st["applicationId"] != application_id:      # 是不是本张申请
if st["owner"] != rec.owner:                    # 是不是这个人
if st["afRef"] != af_ref(rec.af.af):            # 是不是这条记录的 AF
if st["cmi"] != phc1.apm.cmi:                   # 跟 PHC' 里的 CMI 是否一致
if st["phcDigest"] != phc_digest(phc1):         # 是不是这份 PHC'
if g.get("domain2") != st["domain2"]:           # DIDGR 里那个字段是否与声明一致
domain2 = st["domain2"]                         # 只认声明
```

最后一行是关键：**取值用的是 `st["domain2"]`，不是 `g["domain2"]`。** DIDGR 里那个字段降级成了"一致性检查对象"，不再有取值权。

再加一层跨申请复用防护（`issue.py:59-68`）：TP 落盘时记一张 `d4Statements` 表，同一个 `recordId` 只能用一次，第二次换个申请号来重放会被拒。

一句话总结这三段：**域名这张纸条，从"用户递来的"变成了"AP 写的、用户签收的、TP 核对过的"。**

## 四、它说的"变异验证"是什么意思

它说：把 D6 的 domain2 检查临时退回旧写法，`test_d6_rejects_domain2_substitution_in_didgr` 立刻失败。

这在测试里叫变异测试，用大白话讲是：**先把自己刚锁上的门重新打开，看报警器会不会响。响了，说明报警器有用；没响，说明刚才那个测试是白写的。**

这条习惯值得肯定。它比"19 项全绿"有说服力得多 —— 全绿只能证明测试没报错，证明不了测试抓得住东西。

## 六、哪些你不用看懂

分三类，只有第一类跟你的理论有关。

**第一类：跟协议有关，你该看懂**
- D4Statement 为什么必须存在（第三节）
- 为什么取 `st["domain2"]` 而不是 `g["domain2"]`（取值权）
- AP 和用户两把签名覆盖同一份内容，这是"双向制约"的落地

**第二类：工程约束，跟协议无关**
- `assert_single_worker()`（`v1_http.py:139`）拦 `--workers`、`WEB_CONCURRENCY`、派生子进程三件事。
  原因很土：一次性挑战存在进程内字典里（`v1_auth.py:48`），存储的读改写只有本进程的锁（`store.py` 的 `RLock`，没上文件锁）。多开一个进程，这两件事同时失效。
  **这是"当前实现的限制"，不是"协议的属性"。** 以后换成带原子消费的共享存储就能放开，代码里也这么写了。
- 252 项测试、11 项认证契约、19 项攻击用例：回归网，不是理论。
- 256 KiB 限长、字段白名单：接口卫生。

**第三类：你完全不用管的**
- 具体的异常类名、目录分层、dataclass 字段顺序。

## 七、我要更正它的一条说法

它写：

> AP 无法独立核验 `applicationId` —— 那是 TP 的申请号，AR 和 TPAC 里都没有，只能由门户在开会话时传入。所以这个字段是纵深防御，不是锚点。

前半句我核了，**属实**：`ap_open_ar`（`proto_ap.py:46-77`）读的是 AR 和 TPAC，TPAC 的 body（`proto_tp.py:157-164`）里确实没有 `applicationId`。

但后半句的推论不对。**这不是"物理上核验不了"，是"当前 TPAC 里没放这个字段"。**

TPAC 是 TP 在 G3 签的。签的时候 TP 手里就有申请号 —— `issue.py:30` 的 `c.identity.opened_for_issue(app_id)` 拿到的就是它。只要在 TPAC body 里加一行 `"applicationId": app_id`，AP 验 TPAC 签名时就能顺带拿到一个 **TP 背书的**申请号，D4Statement 里的这个字段立刻从"纵深防御"变成真锚点。

那要不要改？我的判断是**这一轮不改**：

- AFRef 已经挡住了真正要紧的事（跨凭证复用）。AF 每份申请唯一，D6 对齐 AFRef，声明换不到别的申请上去。
- 号填错只会让 D6 拒绝，是自伤，不是攻击面。
- 改 TPAC 会动签名域，历史测试向量要重算，代价大于收益。

但要把这条记进 `docs/protocol-errata/tpaa_v1.md`，写清楚：**`applicationId` 目前不是锚点，只在 D6 做一致性检查，别让后来人以为它被 TP 背书过。**

它把限制写进注释（`v1_app.py:95-100`）这点做得对 —— 没假装它是强绑定。

## 八、它关于 Portal 的自我披露，也是准确的

我核了三处：

| 域 | 签发方 | 种子来源 | aud |
|---|---|---|---|
| TP | `identity_service/app.py:86` | `TPAA_V1_HSM_SEED` | `tpaa:tp` |
| AP | `v1_app.py:274` | 同理 | `tpaa:ap` |
| 用户区 | `production.py:103-104` | `TPAA_USER_AUTH_HSM_SEED` | `tpaa:user` |

域分离是真的：三把不同的种子，三个不同的 `aud`，令牌跨域校验必然失败。B1 也确实消除了"门户离线持着 TP/AP 长期根密钥"这个最糟的情况。

但它说的剩余风险也真：门户自己拿着 `TPAA_USER_AUTH_HSM_SEED`，能签发有效期 `TOKEN_TTL_MIN = 30` 分钟的 user 令牌。门户在线被控，攻击者能在 30 分钟内以你的名义调 user-zone 接口，不需要你的私钥。

这个边界它没有粉饰，是对的。**B1 解决的是"离线持钥"，不是"在线代操作"。** 后者要么靠 B2（每请求签名），要么靠把 user 区的签发搬到别处（比如用户自己的钱包或硬件），二选一。

## 九、步骤 4 剩下三件事，优先级不一样

它列了三件：operation 固定字段表、256 KiB 限长、requestId 持久幂等。这三件不是同一等级：

1. **requestId 幂等 —— 优先做。** 这是安全属性。`accept-rr` / `accept-final` 现在重放会二次执行，等于一个网络重传就能让同一个申请走两遍 D6。D6 内部有 `if rec.did: raise Conflict` 兜底，但那是在内存状态之后，不是入口处。
2. **字段白名单（缺字段/多字段 400）—— 次之。** 这是接口契约，防的是模糊输入，不是攻击。
3. **256 KiB 限长 —— 最后。** 防的是内存打爆，属于运维健壮性。

如果它要按顺序做，让它把幂等提到最前。
