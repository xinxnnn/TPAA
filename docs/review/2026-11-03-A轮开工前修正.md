# A 轮开工前修正（三条）

> 给编码智能体：这份是对《A 轮实施计划》的补充，不改变 7 步结构。第 1、2 条必须落进计划文本，第 3 条是删减，避免重复劳动。

## 1. 第 2 步的前提不成立 —— 必须改做法

计划写「将 challenge 状态外置到 JsonStore（原子消费）」。**JsonStore 不提供跨进程原子性。**

事实：

- `JsonStore._lock` 是 `threading.RLock`，进程内锁；
- 全仓没有 `fcntl` / `msvcrt` / `filelock` 任一跨进程锁；
- `JsonStore.update()` 是 `load() → fn() → save()`，即 read-modify-write。`save()` 里 `os.replace` 只保证**单次写**原子，不保证**读改写序列**原子。

后果比现状更糟：

| 存储 | 多 worker 下的行为 | 性质 |
|---|---|---|
| 现在的进程内 dict | 挑战在 A 签发、登录落 B → 401 | 可用性故障，一测就现形 |
| 直接换成 JsonStore | 两进程同时 `pop` 到同一条 → 两边都通过 → **签出两个 token** | 安全故障，静默、难复现 |

`AuthIssuer.login` 的第一步就是 `_challenges.pop(...)`，这一步的原子性就是全部保证所在。换成文件后它不再原子。

二选一，选完写进计划：

- **A（推荐，本轮）**：各域服务 `workers=1`，并在启动时断言。`uvicorn` 的 `--workers` 或多进程部署直接拒绝启动，不要只在文档里写一句。理由：这是演示与验收阶段，单 worker 足够跑完整链路，避免在 A 轮顺手自研一把跨进程锁。
- **B**：给 `JsonStore` 加跨进程文件锁（Windows `msvcrt.locking`，Linux `fcntl.flock`），并让"读改写"整体持锁。这是共享基础设施改动，会影响所有用 JsonStore 的服务，**单独一轮做**，不要塞进 B1。

无论选哪个，测试断言必须是：同一 challenge 第二次 login 返回 401，且**并发**（线程或进程）两次 login 只有一次成功。

## 2. 第 7 步低估了 —— phc-service 目前起不来

`services/tp_side/phc_service/app.py:89-92` 的 `_from_env()` 直接 `raise RuntimeError`，注释写明「当前只支持与 TP 其他服务同进程装配（见 `tests/integration/test_tpaa_v1_http.py` 的 `TpDomain`），独立部署待接 HTTP 端口」。

而 A 轮出口要求「真实 loopback socket 拉起单独进程，验证最小用户流程」。**最小用户流程只要含 G3（PHC 签发），就撞在这个 raise 上。**

二选一，写进计划：

- **A**：把「phc-service 接 identity / review 的 HTTP 端口」纳入 A 轮第 7 步的工作量估算，它不是一个 smoke 脚本，是一次服务装配改造（需要 identity 提供 `opened_for_issue`、review 提供 `approval_for` 的 HTTP 形态）。
- **B（推荐，本轮）**：A 轮的 smoke 边界收窄为「executor 独立进程 + B1 认证链路」，G3/D6 仍走同进程 TP 装配，并在报告里明确写「TP 侧尚未独立部署，本轮不覆盖」。这样 A 轮能按期出口，服务拆分的账留到 B 轮或单独一轮。

不要选「先不看这个 raise，跑到再说」——它会在第 7 步变成一次范围外改造。

## 3. 删减：两处不要重复做

**executor 侧已有登录能力，第 1 步不要新增签名接口。**

`services/user_side/executor_service/app.py:51-54` 已有 `POST /v1/executor/login-body`，接受任意 `{challenge}` 并返回：

```json
{"challenge": "...", "signPk": "...", "sig": "..."}
```

与 `services/shared/v1_auth.py:113-115` 的 `login(challenge, signPk, sig)` 三个 Body 字段**完全对齐**，可直接转发。`UserCredentialHandler.login_body` 会把 `challenge["aud"]` 带进签名，跨域错用会被目标域拒绝。

**TP/AP 业务端点已全部挂鉴权，不要"补鉴权"。**

已核实：TP identity 5 处（`guard.require("user")` / `"reviewer"`）、AP agent 5 处、phc 2 处、review 2 处、supervision 5 处、portal 4 处，`require_owner` 也在 phc 的 issue / finalize 上。B1 不需要新增这一步，收益直接成立。

## 附带两条，写进 RUNNING.md 即可

- **一个 executor 进程只持有一个 owner**（`TPAA_EXECUTOR_OWNER`）。`/v1/executor/login-body` 是唯一不做 owner 校验的端点（其余都校验 `ctx.handler.owner`），单 owner 前提下无歧义，但「多用户共用同一 executor」这条路必须明确堵死：多用户 = 多进程多端口。
- **`issue` 已有部分幂等**：`services/tp_side/phc_service/domain/usecases/issue.py:27-28` 对已签发申请抛 `Conflict`（→409）。所以第 5 步不需要「禁止再次签发」，只需补 `issuing` / `issue_failed` 两态，覆盖「计算成功但写库失败」这一种。
