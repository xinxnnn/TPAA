## 1. 前提写错了：B1 的服务端已经存在，这一步是删代码不是加接线

计划第 1 步写：

> 若现有域服务无法独立提供登录端点，则先补统一认证接线并在未配好时 fail closed。

**这个前提不成立。** `/v1/auth/challenge` 与 `/v1/auth/login` 已经装在三处：

- `services/tp_side/identity_service/app.py:29` → `install_auth_routes(app, auth)`
- `services/ap_side/agent_service/v1_app.py:269` → 同上
- `services/user_side/portal_api/app.py:342` → 同上

而 `AuthIssuer.challenge()/login()` 已经做完了 B1 需要的全部语义（`v1_auth.py:49-65`）：挑战一次性（`pop` 先作废）、TTL 5 分钟、`aud` 随挑战下发、`check_login` 验签。**服务端一行不用改。**

### 更要紧的一条：Portal 现在那两把钥匙，根本不是 TP/AP 的钥匙

```python
# production.py:68-71（Portal）
tp_auth = AuthIssuer(issuer_hsm=hsm_from_seed("AUTH", "TPAA_TP_AUTH_HSM_SEED"), aud="tpaa:tp")
```

```python
# tp_side/identity_service/app.py:84（TP 自己）
auth=AuthIssuer(issuer_hsm=hsm_from_seed("AUTH"), aud="tpaa:tp", ...)
```

`hsm_from_seed(domain, env_var="TPAA_V1_HSM_SEED")`（`v1_http.py:147`）——TP 用的是**默认环境变量 `TPAA_V1_HSM_SEED`**，Portal 用的是 `TPAA_TP_AUTH_HSM_SEED`。**两把不同的私钥。**

所以 Portal 签出来的 `aud=tpaa:tp` 令牌，TP 的 `AuthVerifier` 用自己那把 `issuer_pk` 验，**必然 401**。

**这条把问题的性质改了**：不是"这条生产路径不安全"，是"这条生产路径从来没通过"——`ServiceHttpPort` 对 TP/AP 的第一次调用当天就会失败。这也解释了为什么它一直没被发现：没人跑通过它。

对计划的影响：

- 第 1 步的工作量**比计划估计的小得多**，主体是删掉 `production.py:66-71` 那四行 issuer 构造、把 `ServiceHttpPort` 改成"先取挑战→执行器签→提交 login→用返回 token"。
- 第 5 步的"核实三个 env 不在 Portal 装配中出现"应该**升格成断言**，而不是人工核对（见 §5）。

## 2. 必然踩到的陷阱：`_challenges` 是进程内字典

```python
# v1_auth.py:47
_challenges: dict = field(default_factory=dict)
```

`challenge()` 写进本进程内存，`login()` 从本进程内存里 `pop`。**只要服务以多 worker 运行，挑战在 A worker 签发、登录落到 B worker，就是 401「挑战不存在、已用过或已过期」。**

这个失败长得**和"签名错了"一模一样**。B1 一上线就会有人（包括编码智能体和后续的答辩演示）把它误判为"用户密钥/签名算法有问题"，然后去改密码学层——实际上跟密码学毫无关系。

必须在计划里写死一条：**B1 落地的前置条件是把挑战状态挪出进程内内存**，三选一：

1. 落 `JsonStore`（与现有存储一致，最简单，单机够用）；
2. 服务端只跑单 worker，并在启动脚本里断言 `workers == 1`；
3. 挑战改为无状态（HMAC 自校验 + 时间窗），但会牺牲"一次性"的强语义。

推荐 1，并且**同时把 `AuthIssuer` 的 `_challenges` 从 dataclass 字段改成外部 store 注入**——否则测试里每个 `AuthIssuer` 实例各有一份挑战表，测出来的东西和线上不是一回事。

## 3. 两处安全精度不足

### 3.1 D5 没写"用户端验 AP 签名" → 用户盲签

计划第 2 步：

> 让声明随 PAR 返回；D5 原样携带到 DIDGR 且由用户签名覆盖；TP D6 验 AP 签名……

**只有 TP 验。** 那用户在执行器里做的"打开 PAR、核对 CMI 与模块清单"（方案第 3 节）核对的是什么？如果核对的是未签名的 PAR 内容，而携带进 DIDGR 的是 statement，两者可以不一致——**用户核对了 A，签的却是 B**。这正是"界面产物必须来自已完成的密码学步骤"想禁止的事，只不过发生在执行器里而不是浏览器里。

要求：**D5 必须在执行器内验证 AP 对 statement 的签名，并逐项比对 statement 的 CMI / ordered modulesDigest / afRef 与 PAR 解出的内容，任何不一致 fail closed；用户确认的对象是"我已验签的 statement 摘要"。**

### 3.2 TP 没有校验"用户签名覆盖了 statement" → 同类 statement 可互换

计划说"从可信声明读取 domain2/CMI，不采用 DIDGR 未认证字段"。方向对，但缺一条：**TP 必须验证 DIDGR 的用户签名覆盖范围包含 statement 全文（或其规范化摘要），并且用它和收到的 statement 逐字节比对。**

不这么做的后果：同一用户、同一 AF（AF 在 G1 固定）、两次不同模块选择的 D4，会产生两条**都合法**的 statement。用户签的是选 A 的那条 DIDGR，攻击者把选 B 的 statement 拼进去——TP 验 AP 签名通过、验 owner/公钥/afRef 全通过，**签发一张绑定到用户没选过的能力集的 DID**。

`applicationId`/`recordId` 在 statement 里，能挡住跨申请拼接；但**同一申请内换 statement**（若 AP 为同一 application 产出过多条，比如重试）挡不住。所以别把安全性全押在 id 上：**签名覆盖范围要显式包含 statement 摘要，测试要覆盖"同 application 换 statement"这一条**。

## 5. 把"核实"换成断言

第 5 步写的是"核实三个 env 不在 Portal 装配中出现"。**人工核实会漏，而且漏的方式很隐蔽**——上次那条 `TPAA_USER_HSM_SEED` 的 grep 就是例子（不读凭证密钥了，但仍在读 `TPAA_USER_AUTH_HSM_SEED`）。

落成三条自动断言：

```python
# 1) 结构断言：Portal 进程里不允许存在 aud != "tpaa:user" 的 issuer
def test_portal_cannot_mint_domain_tokens():
    ctx = build_context(clock=SystemClock())
    assert ctx.auth.aud == "tpaa:user"
    with pytest.raises(AttributeError):
        ctx.auth = AuthIssuer(issuer_hsm=..., aud="tpaa:tp")   # 或者断言签名里没有 aud 参数

# 2) 行为断言：拿 Portal 自签的令牌打 TP，必须 401
def test_portal_signed_token_is_rejected_by_tp():
    tok = portal_ctx.auth.token_for(user_sign_pk)["token"]
    assert TestClient(tp_app).get("/v1/keys", headers={"Authorization": f"Bearer {tok}"}).status_code == 401

# 3) 源码断言（最弱，但兜底）
assert "TPAA_TP_AUTH_HSM_SEED" not in Path("services/user_side/portal_api/infra/production.py").read_text()
```

第 2 条是真正有价值的：它证明的是**行为**，不是"文件里没出现某个字符串"。

顺带：`execution_profile` 默认值反转（上一轮 P2）没有出现在这版计划里。第 1 步应写明——默认 `"test-adapter"`，且用测试断言 `/api/user/v1/initialize` 返回 `userControlledExecution == false`。

## 6. 一处漏项：`issue()` 没有补偿，而新链路让失败面更大

上一轮提过、这版计划没有吸收：`portal_api/app.py:194-202` 三步（TP 签发 → 执行器 `accept_rr` → 本地 `_save`）中任何一步失败，都会留下**TP 已签发但门户不知情**的状态。重试会再次打 `/issue`。

第 1 步给每次域调用加了"取挑战 → 签名 → 登录"三段，第 2 步又在 D6 前多了 statement 传递——**失败点从 3 个变成 8 个**，而补偿机制仍然没有。

这不要求这轮做完整对账，但要求两件最小的事：

1. **加 `issuing` / `issue_failed` 两态**，失败时把上游错误码原样落库，给一个显式 `retry_issue` 入口（不自动重试）；
2. **明确 401 不自动重试**。令牌 30 分钟过期（`TOKEN_TTL_MIN = 30`），流程里用户在 D5 停留久了就会 401。惰性刷新令牌是对的，但**"收到 401 就重放请求"只允许发生在幂等操作上**——`/issue`、`/finalize`、`/publish` 都不是。要么改用 requestId 幂等键，要么只允许"刷新令牌后重发一次、且仅限 GET"。

同一处还有两个小问题，顺手一起清：`timeline()` 是 GET 却写库，且 `:161-162` 连续两次 `_save`；`_next_action` 看 `events`、`confirm_d5` 看 `row["state"]`，**一个流程两套状态判据**。这轮新增的 `issuing/issue_failed` 正好是收口时机——统一到 `row["state"]`，`events` 只做展示。

## 7. D4Statement 的两个设计细节建议改

### 7.1 用"一次性绑定"代替"短期有效"

计划写"短期有效的声明"。但 D4→D6 之间隔着 **D5 的人工确认**，而人工确认的耗时不归系统管。TTL 定短了，用户多看一眼就过期；定长了，"短期"失去意义。

改成：**statement 以 `recordId` 为单次凭据，TP 侧记录 `statementUsed`，用过即拒；`issuedAt` 只做一个宽松上限（如 24h），不做硬 TTL。**

好处是消除两类问题：用户迟疑导致的合法失败、测试里的时钟抖动（flaky）。

### 7.2 错误码要能区分"过期"和"伪造"

现在所有拒绝都会落到同一条 message。要求：statement 过期/已用 → `409`（可重试，语义是"重新走 D4"）、签名不符 → `403`（不可重试，可能是攻击）。两者合并，前端就没法提示用户该怎么办，安全日志也没法区分噪音和攻击。

## 8. 第 3 步有一句合并残留

第 3 步：

> 为未来 B1 的 sign-challenge 留清晰接口，避免 Portal 代理协议操作越权

**B1 在第 1 步就已经做了。**这句是上一版计划（那时 B1 还没定）的残留。留着它的后果是：编码智能体会再建一套"将来用的"签名接口，与第 1 步刚接好的 `/v1/auth/challenge` 重复，然后两套各自演化——这正是 `executor_http.py` 里两份客户端分叉的同一个剧本。

删掉，或改成"执行器的 challenge 签名入口即为 B1 接口，不得另建第二套"。

## 9. 范围建议：拆两轮，中间设硬门槛

8 步里有 4 个独立交付物（认证 / 协议 / 执行器 / 发布+runtime+前端）。第 6、7、8 步都依赖第 1、2 步定型，一起开工的话，前面一改，后面全返工。

**A 轮（本轮）**：第 1、2、3、4、5 步。

出口门槛（全绿才进 B 轮）：

- `test_portal_cannot_mint_domain_tokens` + `test_portal_signed_token_is_rejected_by_tp` 通过；
- 多 worker 下 challenge→login 不断（或启动脚本断言单 worker）；
- `grep -c "_applications" executor_http.py` → 0；
- 两份 transport 跑同一套 executor 契约断言；
- D5 验签 + 同 application 换 statement 的攻击用例通过；
- `RUNNING.md` 能照着起 executor，并写明 `profile=test-adapter`、`keys.json` 明文、loopback+共享 token 的威胁边界。

**B 轮（下一轮）**：第 6、7、8 步。

**B1 的威胁模型要在 A 轮就写进 RUNNING.md**，措辞建议：

> B1 消除的是"门户离线持有 TP/AP 长期根密钥"。它**不**消除"门户在线时被控、在令牌 30 分钟有效期内代该用户调用 TP/AP"。要消除后者需要每请求签名（B2）或门户与执行器之间的硬件隔离。

不写这句，B1 会被当成"认证问题已解决"，而那正是这次要避免的那种自述。
