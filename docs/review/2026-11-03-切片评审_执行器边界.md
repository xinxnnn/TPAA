## 0. 结论

**方向对，但现在的完成度是「形状做了一半」。** 传输层确实从同进程调用换成了 HTTP，可是**装配层、拒绝语义、契约测试三处还停在旧形状**。按现状继续往下加功能，这三处会全部返工：

1. 绑定校验在服务端是**可选的**，不传就跳过；
2. 生产装配**默认自称「用户独立控制」**；
3. `PortalContext.handlers` 是「启动时构造的进程内对象字典」，而执行器已经是远程进程了——**这个形状装不了远程执行器，也装不了第二个用户**；
4. 两份客户端已经分叉，且**测试路径比生产路径宽松**；
5. 所有业务拒绝都塌成 **500**。

在这些之上再加「幂等」「独立进程」「联合测试」，等于在歪的地基上砌墙。

## 2. 五个必须先改的问题

### P1 · 绑定校验在服务端是可选的，等于没有

```python
# executor_service/app.py:69-76
app_id = body.get("applicationId")
if operation == "set-application":
    ...
elif app_id is not None and ctx.handler.application_id(execution_label) != app_id:
    raise HTTPException(403, "executor application mismatch")
```

`app_id is None` 时**整段跳过**。而 handler 自己不做 application 校验（`accept_g4`、`build_ar`、`accept_final` 全部只按 `label` 取记录，`handler.py:90-98, 130-137`）。

后果：任何持有 token 的本地调用者，只要**省略** `applicationId` 字段，就能在一个已经绑定到应用 A 的 label 上推进流程。这不叫"绑定可被替换"（`handler.py:113` 确实挡住了替换），而叫**绑定可被无视**——而切片第 1 步要的正是"由执行器持久状态权威校验"。

`ExecutorHttpClient` 因为本地要求预绑定（`executor_http.py:76-82`），所以总是带 `applicationId`；**这条绕过只在对手手里才出现，测试永远看不到**。

修法（服务端为准，不依赖客户端自觉）：

```python
APP_SCOPED = {"accept-rr", "accept-g4", "build-ar", "open-cmm", "build-paci",
              "accept-par", "build-didgr", "accept-final", "publication-receipt"}
if operation in APP_SCOPED:
    if not isinstance(app_id, str) or not app_id:
        raise HTTPException(409, "executor operation requires applicationId")
    bound = ctx.handler.application_id(execution_label)
    if bound is None:
        raise HTTPException(409, "executor label is not bound to an application")
    if bound != app_id:
        raise HTTPException(403, "executor application mismatch")
```

# portal_api/app.py:105-111
"executionProfile": self.ctx.execution_profile,

return PortalContext(wallet_root=..., store=..., tp=tp, ap=ap, phc=phc,

默认值应当反转为最保守的那个（`"test-adapter"`），生产要显式声明才升级。这类"安全默认"的默认值方向，比任何注释都重要。

### P3 · `PortalContext.handlers` 是进程内对象字典，装不了远程执行器

```python
# portal_api/app.py:63-70
handlers: dict[str, ProtocolExecutor] | None = None   # → {}
```

```python
# portal_api/app.py:77-80
def _executor(self, owner: str) -> ProtocolExecutor:
    if owner not in self.ctx.handlers:
        raise RuntimeError("当前部署未配置独立的用户端协议执行器")
```

三件事叠在一起：

**① 生产装配根本没填这个字典**（`production.py` 全文没有 `handlers=`）。所以"生产无装配"只是往前挪了一步：进程能起来、`/healthz` 通、公钥也能通过 HTTP 取到，**第一次调 `/initialize` 就 500**。这比启动即失败更坏——启动成功会让人以为装配好了。

**② 形状是错的。** `handlers` 是「启动时构造好的对象」，可执行器现在是**远程进程**。远程执行器的客户端需要 `(base_url, token, owner)`，其中 `owner` 来自**已认证的会话**，不是启动配置。用启动期字典装它，只能装一个固化 owner（`production.py:62` 的 `TPAA_EXECUTOR_OWNER`）——**即单用户门户**。要支持第二个用户，得重写这个字段和所有取用点。

**③ 重启即死。** `self._applications` 是客户端进程内存（`executor_http.py:20`），`_application()` 查不到就抛（`:79-81`）；而执行器**没有**"查询当前绑定"的端点（`executor_service/app.py` 只有 `/public-key`、`/login-body`、`/build-cr`、`/{operation}`）。门户重启后 `executorLabel` 还在自己的库里（`portal_api/app.py:131`），但客户端不知道绑定，所有后续操作直接失败。验收里那条「服务重启及密钥不变」**按现状必然不过**。

修法：把 `handlers` 换成工厂，绑定改为**向执行器求证**而不是本地记忆：

```python
# PortalContext
executor_for: Callable[[str, str], ProtocolExecutor]   # (owner, session) -> client
# ExecutorHttpClient._application
def _application(self, label, owner):
    bound = self._request("GET", f"/v1/executor/{label}/application")["applicationId"]
    if bound is None:
        raise RuntimeError("executor label has no application binding")
    return bound
```

`set_application` 已经是同值幂等（`handler.py:112-116`），所以重启恢复只需重绑一次，成本很低。

### P4 · 两份客户端已分叉，且测试路径更宽松

| 方法 | `ExecutorHttpClient` | `_TestExecutorHttpClient` | 影响 |
|---|---|---|---|
| `public_signing_key` | 校验 owner（`:45-46`） | **不校验**（`:156-157`） | 门户的归属校验在测试里被短路 |
| `_application` | 未绑定 → 抛错（`:79-81`） | 允许传入，并**写入本地绑定**（`:195-198`） | `set_application` 可被跳过 |
| `build_cr` | `**kwargs`（`:52-56`） | 显式 8 个参数（`:162-168`） | 签名不同，改一处漏一处 |
| `_call` 校验 | 本地绑定必须一致 | `not in (None, app_id)` → **None 放行** | 见 P1 同一类漏洞 |

251 行里约 100 行是复制粘贴。已经分叉，而且分叉方向统一是"测试更松"——这意味着**测试通过什么也证明不了**。

修法：shim 只覆写传输，不覆写语义。

```python
class TestExecutorHttpClient(ExecutorHttpClient):
    def __init__(self, client, token, owner):
        self.client, self.token, self.owner = client, token, owner
        self.base_url, self.timeout, self._applications = "testclient://", 5.0, {}

    def _request(self, method, path, body=None):
        r = self.client.request(method, path, json=body,
                                headers={"Authorization": f"Bearer {self.token}"})
        ...
```

这样两份客户端**不可能**再分叉，且 contract test 天然覆盖到真实客户端的全部逻辑。

### P5 · 所有业务拒绝都塌成 500

`CredentialHandlerError` 继承 `RuntimeError`：

```python
# user_credential_handler/handler.py:38-39
class CredentialHandlerError(RuntimeError):
    pass
```

`install_errors` 只映射了 `Unauthenticated / NotFound / Conflict / Forbidden / ProtocolError / PkeError / SlotError / PermissionError / ValueError`，其余落到 `Exception → 500`（`v1_http.py:57-69`）。

于是"绑定不能被替换"（`handler.py:114`）、"当前处于 X 阶段"（`handler.py:234`）、"没有这个申请"（`handler.py:232`）**全部返回 500 内部错误**。同一路由里 `args["rr"]`、`args["appId"]` 缺字段时抛 `KeyError`，也是 500（`executor_service/app.py:79-91`）。

这直接违反方案里「拒绝、错误顺序、重放、替换一律 fail closed」——fail closed 是安全属性，但**返回码是契约**。现在客户端无法区分"我操作错了"和"服务崩了"，`ExecutorHttpClient` 只能一律翻成 `RuntimeError("...HTTP 500: 内部错误")`（`executor_http.py:36`）。

最小修法：executor 内注册两个映射，并把路由体改成显式校验。

```python
from user_credential_handler import CredentialHandlerError
@app.exception_handler(CredentialHandlerError)
async def _ch(_: Request, exc: CredentialHandlerError):
    return JSONResponse(409, {"code": 409, "message": str(exc)})

REQUIRED = {"accept-rr": ("rr",), "build-ar": ("expires",), "open-cmm": ("cmm",),
            "build-paci": ("selection",), "accept-par": ("par",),
            "build-didgr": ("expires",), "accept-final": ("final", "attestation"),
            "set-application": ("appId",)}
# 缺字段 → 400，多余字段 → 400（不要静默丢弃）
```

### 4.1 `production.py` 的 docstring 与代码相反

## 5. 事务性：`issue()` 的三步没有补偿

```python
# portal_api/app.py:194-202
issued = self.ctx.phc.post(f"/v1/phc/{app_id}/issue", {}, owner)          # ① TP 已签发
executor.accept_rr(row["executorLabel"], issued["rr"], owner=owner, ...)   # ② 可能失败
row["events"].append({... "G3" ...}); self._save(row)                      # ③ 失败则无记录
```

②失败 → TP 侧已经有 PHC 记录，门户侧 `_next_action` 仍是 `issue` → 重试再打 `/issue`。TP 是否幂等需要确认；若不幂等就是重复签发，若幂等则要看它返回的是不是**同一份** RR（否则 ② 会接受一份与 ① 不同的凭证）。

方案第 3 点要求"跨服务失败写入 pending/failure 并提供对账路径"，那是后面的事。**但当前切片至少要保证失败不留不可恢复状态**，否则每失败一次污染一次库。最小做法：三步之间先写 `{"state": "issuing", "attempt": n}`，失败落 `issue_failed` + 原始错误码，并给一个 `retry_issue` 显式入口（不自动重试）。

同类问题：`timeline()` 是 GET，却写库（`:161-162` **连续两次 `_save`**），读-改-写跨了两次加锁（`store.py:47-67` 每次 `load()` 独立加锁）。两个标签页同时刷新可能互相覆盖 `events`。这不是当前切片的必修项，但 `_next_action` 看 `events`、`confirm_d5` 看 `row["state"]`（`:284`）——**同一个流程有两套状态判据**，这是后面所有"状态不一致"类 bug 的源头，建议这轮先统一到一套。

## 6. 建议收敛后的切片

**本轮做（只这五件，做完能独立验收）**

1. 服务端绑定校验改为强制 + 新增 `GET /v1/executor/{label}/application`；客户端删掉 `_applications` 内存字典，改为向执行器求证。
2. `execution_profile` 默认改为 `"test-adapter"`；`production.build_context` 显式传 `"test-adapter"`，并在 `initialize` 里区分「profile」与「真实密钥控制」两个字段，后者恒为 `false` 直到有真执行器。
3. shim 改为继承 `ExecutorHttpClient`，只覆写 `_request`；删掉约 100 行重复。
4. executor 路由加 `REQUIRED` 表 + 未知字段 400 + `Content-Length` 上限（如 256 KiB）+ `CredentialHandlerError → 409`；`accept-final` / `accept-rr` 加 requestId 幂等记录。
5. 新增 `tests/integration/test_executor_contract.py`：用**同一个** transport 参数化跑两份客户端，覆盖 401 / 403 跨 owner / 403 跨 application / 409 未绑定 / 400 缺字段 / 413 过大 / 顺序错 / 敏感字段不出现在响应与日志。

**本轮不做**

- 独立进程 socket smoke（放到 P1–P5 之后，因为它要求接口先稳）
- `issue` 的对账路径（但**要做** `issuing`/`issue_failed` 两态，避免污染）
- 认证域分离（那是上一份评审的 P0，独立一轮）

**验收怎么算过**

- 删掉 `handlers` 里的假执行器，`/initialize` 必须返回明确的"未配置执行器"而不是 500；
- `grep -c "_applications" executor_http.py` → 0；
- contract test 对**两份**客户端都跑通同一批断言；
- `RUNNING.md` 里能照着启动 executor，且写明 `profile=test-adapter`、`keys.json` 是明文种子。
