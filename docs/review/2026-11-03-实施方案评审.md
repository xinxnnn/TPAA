## 0. 结论

**方向对，但有三个地方会让你做无效功，还有一个洞比方案列的所有项都严重。**

- 主干成立：分层推进、fail closed、证据契约公开可读、发布绑定 D6、runtime 去掉 TP/AP HSM —— 这几条都对，而且和代码现状对得上。
- **但方案把两件已经做完的事写成"未做"**（D1–D6 的链路测试、publication 的证明校验），照它做会重复劳动。
- **方案把一件必须做的事写成"若需要"**（D6 绑定 D4）。按代码，这是必选，不补的话第 4、5 条赖以成立的"证明链"是断的。
- **方案漏了一个认证层的洞**：门户进程持有 TP / AP 的令牌签发种子，谁跑门户谁就能冒充任意自然人访问 TP 与 AP。这一条不修，"三域独立"在认证层就已经不成立，后面所有边界硬化都是给一扇门加固，而门后站着一个能签任何人令牌的进程。

一句话：**方案的骨架可以用，但第 1 项要换成认证域分离，第 3 项里的"若需要补字段"要改成"必须补，字段如下"。**

## 2. 三处事实错误（会直接导致排期浪费）

### 错 1 ·「两个 workflow test 只证明 G1–G4 片段」

**核对结果：不成立。第二个测试已经从 D1 跑到 publish。**

`test_portal_api_runs_d1_through_publish_from_real_cmm` 的断言链覆盖 D1 → D2 → D3 → D4 → D5 → D6 → publish，并直接断言了阶段集合：

```
assert {event["stage"] for event in d4.json()["events"]} >= {"D1","D2","D3","D4"}
assert d6.json()["nextAction"] == "publish"
assert published.json()["state"] == "published"
```

依据：`tests/integration/test_user_workflow.py:54-110`。

**这句话的代价**：按方案字面理解，会去补一套"D1–D6 的链路测试"，而实际已有的缺口只有一个——**它是同进程 TestClient，不是真实 socket**。要补的是「跨进程」，不是「跨阶段」。这两个工作量的量级差一个数量级。

**准确的表述应该是**：D1–D6 的**逻辑链路**已验证；未验证的是**进程边界**：真实 HTTP、独立进程启动、重启后状态恢复、执行器与门户真的分成两个 PID。

### 错 2 ·「AP publication 当前未验证最终制品」

**核对结果：不成立。它验证了，而且验得比方案描述的更细。**

`publish()` 实际做了六件事：

1. 取 TP 签名的 `FinalizationAttestation`，用 `tp_sign_pk` 验签（`:163-168`）；
2. 逐字段比对 `applicationId / owner / userSignPk / did / phcDigest / cmi` 与钱包回执一致（`:169-171`）；
3. 校验回执里的用户公钥归属人 == D4 记录 owner（`:172-174`）；
4. 校验 `cmi` == AP 自己在 D4 记录的 cmi（`:175-176`）；
5. 校验 `modulesDigest` == D4 记录的有序模块摘要（`:177-180`）；
6. 已发布则直接返回旧记录（幂等，`:181-184`）。

依据：`services/ap_side/agent_service/v1_app.py:151-215`。

**所以它的问题不是"没验证"，而是"验证完之后把源码明文写进记录并回显"。** 这是产出物形态问题，不是证明链问题。两者的修法完全不同：前者要补校验逻辑，后者要改成「只存 digest + 制品库引用」。方案按前者理解会做错方向。

### 错 3 ·「runtime trust 要重写」

**核对结果：方向对，改动面被说大了。**

`trust.py` 的两个核心函数签名已经是「接 HSM → 出可独立验签的 `SignedStatement`」：

```
tp_bind_did(*, tp_hsm, did, phc_doc, now, ttl) -> SignedStatement   # :78
ap_attest_runtime(*, ap_hsm, ap_record, phc_doc, manifest, ...) -> SignedStatement  # :95
```

返回体是 `{body, sig}`，签名 tag 分别是 `RT/DidBinding` 与 `RT/Attestation`，验证方只需要公钥。**这个接口形状本身就是对的**，符合方案第 5 条要的"只接公钥、签名证明"。

要改的只有一件事：**HSM 从哪来**。把「同进程对象」换成「HTTP 取回一段已签声明」。`manifest.py` / `runtime.py` / `sandbox.py` 基本不动。

**这句话的代价**：按方案理解会重写四个文件，实际是一个注入点。

## 3. 方案没发现的三处问题

按严重度排序：B 最严重，A 最容易被问倒，C 最容易被写成"已实现"。

### 问题 A · D6 没有把 D4 绑进去，而且现有字段补不上

方案第 1 条写的是：

> **若**现有消息未携带将 application、D4 record 和 D6 结果密码学绑定所需字段，**先**在 v1 协议契约和测试中明确最小补充。

语气是"若有需要"。核对后：**这是必选，而且是 D6 唯一的实质缺口。**

**代码事实三条：**

1. `TpRecord` 没有 `domain2`、没有 selection、没有 D4 记录引用；`cmi` 字段在 `tp_issue` 时是空的，要到 `tp_finalize` 之后才写入。
   依据：`proto_tp.py:114-129`（字段表）、`:165-168`（构造时不传 cmi）。

2. `tp_finalize` 对 PHC' 的全部约束只有两条：`phc1.tpm.af == rec.af.af` 和 `phc1.apm.af_ref == af_ref(rec.af.af)`。
   依据：`proto_tp.py:198-199`。

3. `domain2` 直接取自 DIDGR 的明文字段，**没有任何签名或摘要约束它**。
   依据：`proto_tp.py:203`（`did = f"did:wba:{...}:{domain1}:{g['domain2']}"`）、`proto_user.py:187`（`"domain2": verified.domain2`，而 `verified.domain2` 来自 PAR 明文，PAR 只加密、未签名 —— `proto_ap.py:121-123`）。

**先说清楚这个洞不是什么。** AF 在每次 G1 时重新生成（`commit_af(hid, a_pub, t_pub, r=rand_exp())`，`proto_user.py:60`），所以不同申请之间的 AF 不同，`phc1.tpm.af == rec.af.af` 这一条**能挡住跨申请拼接**。方案担心的那个攻击在这一层不成立。

剩下的缺口只有一条，但它足够严重：

**`domain2` 不受任何约束。** 用户可以拿着应用 A 的合法 PHC'，把 DIDGR 里的 `domain2` 改成任意 AP 的域名，TP 会照单全收，生成一个 `did:wba:<CSCID>:domain1:<任意AP域名>` 的 DID。而 AP 侧 `publish()` 拿 `receipt["did"]` 直接去 `assemble(did=...)`，**也不校验 domain2 是不是自己的**（`v1_app.py:187-189`）。

**攻击路径（三步，全部通过现有校验）：**

1. 用户在 AP-A 完成 D4，拿到合法 PAR / PHC'；
2. D5 构造 DIDGR 时把 `domain2` 换成 `ap-evil.example`，用自己私钥签名（合法，因为域名不在任何签名覆盖范围内）；
3. TP 验签通过、AF 匹配通过、CMI 非空通过 → 签发 DID，写入 `rec.did`，返回 FINAL。

结果：一张由 TP 正式签发、指向任意域名的 DID。**TP 对此完全无感，因为它在协议里没有任何独立来源可以核对 domain2。**

**最小修法（这是唯一自洽的解法）：**

在 D4 让 AP 签一份记录声明，D5 带上，D6 验它：

```
D4Statement = Sign_skap({
  "v": "tpaa-v1-d4",
  "applicationId", "recordId",
  "owner", "userSignPk",
  "afRef", "cmi", "domain2",
  "modulesDigest",
  "issuedAt", "expires"
})
```

- AP 在 `ap_build` 里生成并随 PAR 一起给（PAR 内新增 `d4Statement` 字段）；
- 用户 D5 把它原样带进 DIDGR；
- `tp_finalize` 新增：验 `D4Statement` 的 AP 签名 → 校验 `afRef` 与 `rec` 一致、`owner` 与 `rec.owner` 一致 → **`domain2` 与 `cmi` 一律取声明里的值，不信 DIDGR 的明文**。

这样 TP 不需要"知道 CMI"（它本来就不知道），只需要"信 AP 的签名"。而且正好满足方案第 1 条自己提出的标准：**发布证明必须能由 AP 依据自身 D4 记录核验，不得把不可验证的客户端声明当证明** —— 现在 domain2 就是那个"不可验证的客户端声明"。

**验收用例（必须新增）**：同一份合法 DIDGR，只改 `domain2` 后重签 → 期望 `E_D4_STATEMENT_MISMATCH`。

### 问题 B · 门户进程持有 TP / AP 的令牌签发种子，三域分离在认证层已经塌了

方案从头到尾没提这一条，但它是当前代码里最严重的一处。

**代码事实：**

```python
# services/user_side/portal_api/infra/production.py:66-74
auth    = AuthIssuer(issuer_hsm=hsm_from_seed("AUTH", "TPAA_USER_AUTH_HSM_SEED"), aud="tpaa:user")
tp_auth = AuthIssuer(issuer_hsm=hsm_from_seed("AUTH", "TPAA_TP_AUTH_HSM_SEED"),  aud="tpaa:tp")
ap_auth = AuthIssuer(issuer_hsm=hsm_from_seed("AUTH", "TPAA_AP_AUTH_HSM_SEED"),  aud="tpaa:ap")
```

门户进程**自己**构造了 TP 和 AP 两个域的 issuer。然后：

```python
# production.py:26 —— ServiceHttpPort._request
token = self.auth.token_for(self.user_sign_pk)["token"]
```

而 `token_for` 的注释写得很坦白：

```python
# services/shared/v1_auth.py:69-70
def token_for(self, sign_pk: str) -> dict:
    """按公钥签发令牌（名录里的人员按名录给角色，其余为 user）。调用方负责先认证。"""
```

**`token_for` 不验任何东西**。门户拿着 TP 域的 issuer 种子，可以直接给**任意公钥**签一张 `aud=tpaa:tp` 的令牌，`sub` 就是那个公钥的 owner 指纹。

**后果**：谁跑门户，谁就能冒充任意自然人访问 TP 与 AP。用户域被攻破，等于 TP 与 AP 的鉴权同时失守。这不是"边界没硬化"，这是**边界本身不存在**。

**为什么这条比别的都重：威胁模型被倒过来装了。**

这套系统的攻击者名单里，排第一的就是**恶意用户**——整个课题的卖点就是"恶意智能体可追溯到自然人"。而这里，恰恰是用户域的那个进程，手里握着 TP 的认证根。最需要防的角色拿到了冒充所有人的钥匙。

而且它不是"配错了"，是**代码里的设计**：`AuthVerifier.check` 只用 `issuer_pk` 验签，`require_owner` 只看 `claims["sub"] == owner`，而 `sub` 在 `token_for` 里是由签发方自己算出来的。这三处分别在 `services/shared/v1_auth.py` 的 `AuthVerifier.check`、`require_owner`、`AuthIssuer.token_for`。链路里没有任何一处需要用户真的拥有那把私钥。

**一个必须说清的前提**：`TPAA_TP_AUTH_HSM_SEED`、`TPAA_AP_AUTH_HSM_SEED`、`TPAA_USER_AUTH_HSM_SEED` 这三个变量在整个仓库的启动脚本与文档里都没有配置，只有 `production.py` 引用它们。所以现状是**这条生产装配从未被启用**——这和方案说的"生产无装配"一致。问题在于：它是"生产装配"的唯一实现，一旦按方案第 2 步启用，就是这个效果。

**为什么方案的第 6 条反而在加固这个洞**：

> 交互只调用 user-zone 后端承载的协议操作，不在浏览器执行密码学

这句把"门户代表用户"固化成了架构。可门户凭什么代表用户？现在凭的是"它手里有 TP 的 issuer 种子"。一旦这个种子不该给它（按三域独立的原则本来就不该），整个调用链就得换形状。

**两条修法，必须选一条（不能都做）：**

| 方案 | 做法 | 代价 |
|---|---|---|
| **B1（推荐）** | 令牌由**用户私钥签挑战**换取：门户转发挑战给执行器 → 执行器签 → 门户拿签名去 TP/AP 的 `/v1/auth/login` 换令牌。门户不再持有任何 TP/AP issuer 种子 | 每个请求多一次往返；执行器接口要多一个 `sign-challenge`；但"谁能代表用户"这件事有了密码学依据 |
| B2 | 放弃 bearer 令牌，TP/AP 只看请求体内的协议签名 + TPAC 里的 `userSignPk` | 改动面大（所有端点都要改鉴权依赖），但更彻底 |

**无论选哪条，`production.py` 里 `TPAA_TP_AUTH_HSM_SEED` / `TPAA_AP_AUTH_HSM_SEED` 必须从门户进程里消失**，并在启动时做一次 fail-closed 检查：读不到就报错，而不是"没有就不鉴权"。

**验收用例**：门户进程环境里删除这两个种子，端到端流程仍能跑通 → 证明门户不再依赖它们。

### 问题 C · 执行器的威胁模型没写，"用户独立控制"会在这里被说成成立

现在的执行器是：**loopback + 单一 bearer token**。

这意味着：本机任意进程（包括恶意软件）只要读到 `TPAA_EXECUTOR_TOKEN`，就能代用户签 G1 / D5 / D6。也就是说，「用户独立密钥控制」在本切片里的真实含义是「**用户机器上的任何代码都能控制密钥**」。

这不算错——真正的钱包（MetaMask / ssh-agent）也是这个威胁模型。错的是**没写出来**。方案第 2 条要求"严禁把 server-held test key flow 标为生产或用户独立接受"，同样的标准要适用于 loopback executor：

- 要么加"每次敏感操作弹确认"（这需要 `accept_g4` / `build_didgr` 变成人工交互，不是一次 HTTP 调用）；
- 要么在 `RUNNING.md` 与报告里明确写：**本切片的执行器只防"远程冒充"，不防"本机恶意进程"；用户独立密钥控制的完整含义需要 TEE / 硬件钱包 / 用户确认 UI，本期未实现。**

**判定标准**：如果报告里写了"用户独立控制密钥"而没有这句限定，就是方案第 1 条禁止的那种"冒充"。

## 4. 方向对但缺判据的四个点

这四点方案都提到了，但给的是目标不是判据。实现者拿不到判据就会各自发挥，最后对不上。

### 4.1 「同输入幂等」——现有实现靠"只算一次"，不靠"确定性"

`manifest` 的 `created_at` 进了 `audit.createdAt`，而 `canonical_json()` 覆盖了 `audit` 全字段：

```
manifest.py:93   created_at: str = ""
manifest.py:118  "audit": {"createdAt": self.created_at, ...}
manifest.py:121-122  def canonical_json(self): json.dumps(self._build_payload(), sort_keys=True, ...)
```

也就是说：**同一批模块字节，换一个时间点重建，manifest digest 会变。**

现在的"幂等"是靠 `publish()` 里 `if published is not None: return published`（`v1_app.py:181-184`），即"存过就直接返回旧记录"。这是**缓存**，不是**确定性构建**。

方案第 4 条要的是后者（"buildDigest 对最终纳入构建的规范化路径 + 实际字节计算；同输入幂等"）。判据必须写成：

- `buildDigest` 的输入**只允许**是：排序后的相对路径 + 文件字节 + 模块声明；**不含**时间、主机名、绝对路径、随机数；
- `manifest` 的 `audit.createdAt` **不参与** manifestDigest 计算（或由构建输入显式给定，不允许取 `now()`）；
- 判据：同一输入在**不同时间、不同机器**重建，digest 逐字节相同。测试必须是"重建一次再比对"，不能是"读回上一次的"。

### 4.2 「确定性构建」的其他坑：现在只读一个文件

```python
v1_app.py:185  module_bytes = [(m, ver, c.modules.read_file(m, ver, "engine.py")) for ...]
```

一个模块只取 `engine.py` 一个文件。如果模块是多文件的（`__init__.py` / `tools/*.py` / `data/*`），**其余文件不进 buildDigest** —— 也就是说这些文件可以被替换而 digest 不变。这是"签名了一个子集"的经典错误。

判据：`buildDigest` 必须覆盖**模块目录下的全部文件**，且路径清单本身进摘要（否则可以增删空文件绕过）。

### 4.3 RuntimeAttestation 的防重放没有定义

`ap_attest_runtime` 现在签了 `session_pk`（`trust.py:95-120`），但没绑 nonce 或挑战。

后果：一段合法的 attestation 可以被另一个 session 复用（只要它把自己的 `session_pk` 换成……不行，签的是 AP 给的 session_pk，所以攻击者得让 AP 为他的 session_pk 签）。更现实的问题是：attestation 的 TTL 内，AP 为 A 签的那份可以交给 B？不行，B 没有对应私钥。

真正缺的是**验证方拿到 attestation 后，如何确认它是"为这次启动"签的**。判据要写成：

- runtime 启动时生成一次性 `boot_nonce`，先交给 AP；
- AP 的 `RT/Attestation` 载荷必须包含该 `boot_nonce`；
- 有效期 ≤ 5 分钟，且 nonce 用后即废（AP 侧记一个短期去重表）。

### 4.4 运行中吊销的在线依赖没定义

方案写的是"任何依赖服务状态不可用或证明过期时**拒绝启动**"——只覆盖了启动。

运行中呢？工具调用前是否每次查吊销状态？如果查，TP 不可达时是拒绝（fail closed，可用性归零）还是放行（fail open，吊销失效）？这是必须二选一并在报告里写明的策略，不是实现细节。

**建议**：本地缓存吊销列表（TP 定期推送 + 短 TTL），缓存过期且 TP 不可达 → **拒绝**高权限工具、放行只读工具。并在报告里写清这个分级。

## 5. 建议的执行顺序（这是我和方案分歧最大的地方）

方案把「执行器 HTTP 边界硬化」作为当前切片。**这一步本身没有错，但不该排第一**，理由是问题 B：

- 如果认证模型改成 B1（用户签挑战换令牌），执行器要多一个 `sign-challenge` 接口，它的**职责从"代理"变成"签名机"**；
- 现在的执行器接口（`build-cr` / `accept-g4` / …）是按"代理"设计的，每个操作都要传 application / owner / label；
- **先硬化、后改职责 = 接口白做一遍。**

建议顺序：

| 序 | 工作 | 为什么排这里 |
|---|---|---|
| **1** | **认证域分离**（问题 B）：门户不再持有 TP/AP issuer 种子 | 它决定执行器的职责边界。先定这个，后面的接口才不会返工 |
| **2** | **D6 绑定 D4**（问题 A）：`D4Statement` + `tp_finalize` 校验 | 它是"发布证明"整条论证的地基；不补，第 4/5 条的安全声明都是空的 |
| 3 | 执行器契约硬化（统一 schema、字节上限、requestId 幂等、错误响应） | 此时职责已定，硬化一次到位 |
| 4 | 独立进程 + 真实 socket 的 smoke | 验证 1–3 的装配真的成立 |
| 5 | publication 产出物形态（去源码、内容寻址、`buildDigest` 覆盖全文件、去时间戳） | 依赖 2（要有可信的 did/cmi 来源） |
| 6 | runtime 去 HSM（换成 HTTP 取签名声明）+ boot_nonce | 依赖 5 |
| 7 | 前端真实化 | 依赖 3–6 的状态模型 |

如果这轮只想推一个小切片，可以只做 **3**（执行器硬化），但要接受一个前提：**接口按"签名机"设计**，即预留 `sign-challenge` 与"操作由用户签名触发"的位置。否则第 1 步一来就要重写。

## 7. 如果没有时间全做，只做这一件

理由：答辩时最容易被问倒的一句是「你怎么证明这个 DID 绑定的是这次申请的这套能力，而不是同一用户另一次申请的？」——现在代码答不上来，因为 TP 在 D6 没有任何 AP 侧证据。补上 `D4Statement` 之后，这句话就有答案了，而且它同时把"发布证明"和"runtime 启动校验"两处的信任来源都钉住了。
