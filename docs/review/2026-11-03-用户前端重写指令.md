## 0. 先说清楚：现在还不能做 UI

不是「步骤 4–7 做完就能点」。真实状态是：

| 阻塞 | 事实 | 后果 |
|---|---|---|
| 无 HSM 种子 | 全仓 json 搜 `schnorr_sk` 零命中，`scripts/` 无生成器 | 七个服务全部起不来（`hsm_from_seed` 缺项即 raise） |
| 无启动编排 | `run_demo.ps1` 只起两个 Vite；`production.py` 需 11 个环境变量 | 前端 proxy target 指向没人监听的端口，所有按钮 502 |
| 审核台是假数据 | `tp-web/src/pages/review/index.tsx:17` 写死 `initial: DemoApplication[]` | REVIEW 闸门永远不 approved，用户卡死在「等待核验」 |
| **无申请列表接口** | 只有 `GET /applications/{id}/timeline`，没有 `GET /applications` | **刷新页面，申请就找不回来了**（appId 只活在 React state 里） |
| **G3 不返回完整 PHC** | `issue()` 的 G3 artifacts 只放了 `phcVersion` 和 `rrDigest`，没有完整 PHC 对象 | 「查看完整 PHC」没有数据源，点了只能看到摘要 |

前三个是「跑不起来」，后两个是「做不出工作台」。**五个都得先补，UI 才不是空中楼阁。**

第四、第五条工作量最小：列表数据在 `ctx.store["applications"]`（每条有 `owner`）；完整 PHC 在 phc 服务的 store 里，`issue()` 时已经拿到 `issued["phc"]`，只是没放进 artifacts。

### 任务：重写 `apps/user-web`，做成 TPAA 主流程的协议流程工作台

这不是「美化」，也不是「翻译成大白话」。现有 `apps/user-web/src/App.tsx` 是一份裸调试台（左侧 11 格轨写死协议代号、标题 `TPAA V1 / USER CONTROL PLANE`）。要重写成**流程可见的工作台**：用户能一步步走完整个申请，并且**每一步产生了什么凭证、什么数据，都要直接摊开给他看**。

参照范式是旧项目的 `app/web_user/UserApp.vue`（一份 Vue + Element Plus 写的原始工作台，你若访问不了仓库就按下面描述实现）：

- 顶部一条品牌栏：左品牌名「个人 Agent 申领与管理系统」，右账户区（头像 + 当前账号 + 退出）
- 上方一张「用户基本信息」卡片：一排输入框（姓名、ID、身份证号、Email、Passport、人脸照片上传）
- 主体一张「配置个人智能体流程」卡片，里面是一条**垂直时间轴**，每个节点 = 一个流程步骤，格式固定为：
  - 步骤标题（如「1. 请求 PHC」）
  - 一行操作区：主按钮（执行这步）+「查看详情」按钮（切换展开）
  - 状态标签（待审核 / 已签发 / 成功 等）
  - **「查看详情」点开后，用等宽 `<pre>` 原样显示这一步返回的完整 JSON**（PHC、PA、配置、agent 输出都在这里），这就是「每一步生成什么都要展现」
- 时间轴下方还有「更新 PA 配置」「故障恢复」「多智能体管理」等卡片（tpaa 这轮不要求，留位即可）

**本任务只实现到主流程时间轴 + 身份表单 + 完整产物展开。**

#### 1.1 技术基线

`apps/user-web` 目前只有 `react` / `react-dom` / `react-router-dom`，**没有 UI 组件库**，样式是手写的 `index.css`。**不要引入 Element Plus / Ant Design / MUI 等新框架**，用 React + 手写 CSS 实现时间轴和卡片，风格保持轻量、卡片化、留白充足。时间轴用一棵自定义组件画，不要用现成库。

#### 1.2 主流程时间轴：直接映射后端的 11 个阶段

后端 `GET /{id}/timeline` 返回一个 `events` 数组，每个元素形如 `{ stage, status, at, artifacts }`。**这就是时间轴的数据源，不要在前端另算流程状态**——用 `timeline.state` 和 `timeline.nextAction` 驱动一切。

时间轴的节点**就是这 11 个协议阶段**，但每个节点标题用「中文动作 + 协议代号小字」，例如：

| stage | 节点标题 | 节点状态文案示例 |
|---|---|---|
| INIT | 初始化协议参数 | 已加载 |
| G1 | 提交身份申请 | 已提交，待核验 |
| REVIEW | 等待身份核验（TP 人工审批） | 待审核 / 已通过 / 已拒绝 |
| G3 | TP 签发初始 PHC | 已签发 |
| G4 | 用户接受 PHC | 已接受 |
| D1 | 申请智能体能力 | 已完成 |
| D2 | 接收能力目录（CMM） | 已接收 |
| D3 | 用户确认能力选择 | 已确认 |
| D4 | AP 构建个性化智能体（PAR/CMI） | 已构建 |
| D5 | 用户核验并确认声明 | 已核验 / 待确认 |
| D6 | 最终 DID 与 PHC 签发 | 已签发 |
| PUB | 发布智能体制品 | 已发布 |

**保留协议代号**——这不是给外行看的产品页，是给答辩现场展示工作流程的台子，代号必须可见。但标题主文字用中文动作。

#### 1.3 每个节点：操作按钮 + 查看详情

- **已完成的节点**：默认其「查看详情」内容可一键展开。展开内容是该节点 `artifacts` 的**完整 JSON**（`<pre>` 等宽、可横向滚动、可折叠）。这就是「每步生成什么都要展现，体现工作流程」。
- **当前可操作节点**（由 `timeline.nextAction` 决定）：右侧显示主按钮：
  - `issue` → 按钮「申领 PHC」
  - `accept-g4` → 「接受 PHC」
  - `start-agent` → 「拉取能力目录」（即 `begin-agent`）
  - `build-agent` → 「确认能力并构建」（需要用户先在 D2 返回的 catalog 勾选，再点这个）
  - `accept-d5` → 「核验凭证」
  - `confirm-d5` → 「确认声明并构造 DIDGR」
  - `finalize-d6` → 「提交 DIDGR 并签发最终凭证」
  - `publish` → 「发布智能体制品」
- **D5 必须拆成两个按钮，不可合并**：`accept-d5` 是用户端核验 PAR/CMI/AP 签名，`confirm-d5` 才构造 DIDGR（携带用户对 AP 声明的真实签名认可）。合成一次点击，这个认可就变走过场。
- `issue` 与 `accept-g4` 可以合成一个「申领并领取 PHC」按钮（后台两步），但必须显示两段中间态：「正在签发…」→「正在你的设备验证…」。`finalize-d6` 与 `publish` 同理可合成「生成并发布」，显示两段中间态。
- REVIEW 节点不在这里操作——它由 TP 审核台处理。本页面只显示它的状态；若卡在「待审核」，提示用户「请到 TP 审核台通过」。

#### 1.4 身份表单

放在时间轴上方一张独立卡片，字段与后端 `POST /applications` 对齐：姓名、身份编号（ID）、身份证号（选填）、Email（选填）、Passport（选填）、生物特征摘要（对应 `bi`）。提交调用 `POST /applications`，成功后拿到 `applicationId`，时间轴开始推进。

#### 1.5 「查看完整 PHC」怎么实现（关键）

用户明确要看完整 PHC。但后端 `issue()` 的 G3 artifacts **现在只有 `phcVersion` 和 `rrDigest`，没有完整 PHC 对象**。二选一，挑一处落地：

- **方案 A（推荐）**：在 `issue()` 把 `issued["phc"]` 整个放进 G3 的 `artifacts["phc"]`，`accept_g4` 同理把完整 PHC 透传。这样时间轴 G3/G4 节点展开就能看到完整 PHC。
- **方案 B**：新增 `GET /api/user/v1/applications/{id}/phc`，从 phc 服务的 store 取完整 PHC 返回。

PHC 是颁发给用户的凭证，可展示（旧工作台也是整段展示）。**但这只限于 PHC / DID / CMM / PAR 公开部分；前端不得请求或展示 executor 持有的用户私钥、种子、`s_ap`、变色龙随机数种子等机密**。

#### 1.6 硬约束

1. **流程状态完全由后端驱动。** 用 `timeline.state` / `timeline.nextAction` / `events` 渲染，不在前端写 switch 算流程。
2. **每步产物真实可见。** 「查看详情」展开的是后端 `artifacts` 原样 JSON，不美化、不抽字段、不造假。
3. **不做假数据。** 每个操作按钮必须落到 `POST /{id}/{action}`，每个数字来自真实响应。没有接口的区块明说「尚未接入」，不填 mock。
4. **不碰机密材料。** 私钥、种子、`s_ap`、变色龙随机数种子不进页面、不经浏览器内存。
5. **不假装能启动 runtime。** `publish` 只到「制品已生成」，runtime 启动被发布证明校验挡住前不给按钮。
6. **不吞错误。** 后端 403/404/409/500 都在节点上有可读文案（如「AP 服务未启动，无法拉取能力目录」），不是白屏。
7. **不引入 UI 框架。** 手写 React 组件 + CSS，复用现有 `index.css` 风格。

#### 1.7 先补的后端改动

界面需要它们，现有 5 个路由 + 现有 artifacts 不够：

```
GET  /api/user/v1/applications
     → { items: [{ applicationId, state, createdAt, did?, digest? }] }
     数据源：ctx.store["applications"]，按 owner 过滤
     用途：刷新后不丢申请；未来工作台列表

# 完整 PHC（方案 A 或 B 择一）
# 方案 A：issue()/accept_g4() 的 G3/G4 artifacts 携带 issued["phc"]
# 方案 B：GET /api/user/v1/applications/{id}/phc → 完整 PHC 对象
```

列表接口是纯加法（不改协议、不动签名域）。PHC 改动也只是往 artifacts 多放一个对象。

#### 1.9 验收标准

跑通这一条，才算交：

> 浏览器打开 → 填身份表单提交 →（另一窗口在审核台点通过）→ 时间轴 REVIEW 变「已通过」→ 点「申领并领取 PHC」→ G3/G4 节点展开能看到**完整 PHC JSON** → 点「拉取能力目录」后在 D2 节点看到 CMM、勾选 → 「确认能力并构建」→ D4 节点展开看 PAR/CMI → 「核验凭证」然后「确认声明」（两步）→ D6 节点展开看 DID → 「生成并发布」→ PUB 节点出现制品摘要。

- 每一个已完成的节点，点「查看详情」都能展开该步真实 JSON，不缺字段（尤其完整 PHC）
- 全程不碰命令行、刷新页面不丢申请
- 拔掉 AP 服务再点「拉取能力目录」，节点显示可读错误，不是白屏
- D5 两步是分开的两个按钮，不是合成一个
- 界面保留协议代号（G1/G3/D4/D5/D6…），因为要体现工作流程

#### 1.10 明确不做

- **子智能体派生、吊销、更新 PA**：后端 `services/user_side/` 里 `subagent / derive / revoke` 零命中，一行实现都没有。这轮不画空壳页，留位即可。
- **TP 审核台、AP 控制台**：属于 `apps/tp-web`、`apps/ap-web`，另一轮。
- **runtime 启动**：被发布证明校验阻塞。

## 2. 执行顺序建议

| 序 | 内容 | 为什么在这 |
|---|---|---|
| 1 | A 轮步骤 4 剩余（**幂等优先**） | 演示时手抖/连点会二次执行，时间线乱掉没法答辩 |
| 2 | 种子生成 + 统一启动编排 | 不起服务，UI 无从验证 |
| 3 | `GET /applications` 列表 + **完整 PHC 返回（方案 A 或 B）** | UI 的两个数据来源，尤其 PHC 缺了就看不到完整凭证 |
| 4 | 审核台接真（`review_service` 已有 POST，只缺界面） | 打通 REVIEW 闸门，才有「全程不碰命令行」 |
| 5 | 用户前端重写（本文档主体） | 前四步就绪后，一次做完 |
| 6 | 步骤 5/6/7 | 持久化、contract 测试、socket smoke |

**注意**：第 5 步的前端重写可以和步骤 5/6/7 并行 —— 前端是独立进程，只要 8 个 action 契约不变，不会冲突。

## 3. 一句话总结

旧项目真正的工作台是 `UserApp.vue`：一条时间轴，每一步一个「查看详情」展开完整 JSON。tpaa 后端 `timeline.events` 已经按阶段装好了产物，前端要做的就是把这条时间轴用 React 手写出来，**把 11 个协议阶段摊开、每步产物可见**，而不是翻译成大白话藏起来。
